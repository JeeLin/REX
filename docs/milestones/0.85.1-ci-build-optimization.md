# 0.85.1: CI 构建优化

## Context
0.85.0 确认了 CI 流水线正常工作，但构建耗时较长（docker-agent 和 build-hub 各约 30 分钟）。本里程碑聚焦 CI 构建速度优化，提升开发迭代效率。版本类型：patch（内部工程改进，无新功能）。

## 产品边界
本阶段做什么：优化 CI 构建速度，减少 GitHub Actions 耗时。
本阶段不做什么：不改功能代码、不加新功能、不改产品行为。

## 子任务详细设计

### 1 Docker layer caching 优化

- **功能目标**：为 docker-hub 和 docker-agent 启用 Docker BuildKit layer caching，复用历史构建层
- **文件结构**：修改 `.github/workflows/ci.yml`
- **接口设计**：
  - docker-hub job：在 `docker/build-push-action` 中添加 `cache-from: type=gha` + `cache-to: type=gha,mode=max`
  - docker-agent job：同样添加 GHA cache 配置
  - 确保 `docker/setup-buildx-action` 已配置（当前已有）
- **实现细节**：
  - `cache-from: type=gha` 使用 GitHub Actions cache 作为 Docker layer cache 源
  - `cache-to: type=gha,mode=max` 将所有层（不仅是最终镜像的层）写入 cache
  - 这能显著加速 Rust 编译层、依赖安装层的缓存命中
- **测试标准**：docker-hub 和 docker-agent 构建步骤中出现 `importing cache manifest` 表明 cache 生效
- **提交信息**：`ci: add Docker layer caching for hub and agent images`

### 2 Rust 增量编译复用优化

- **功能目标**：优化 Swatinem/rust-cache 配置，提升跨 job 和跨 run 的编译缓存命中率
- **文件结构**：修改 `.github/workflows/ci.yml`
- **接口设计**：
  - 为 check-rust job 的 rust-cache 添加 `shared-key: check` 使 check 和 build 共享缓存
  - 为 build-agent 和 build-hub 的 rust-cache 配置 `shared-key: build-${{ matrix.target }}` 避免 key 冲突
  - 添加 `save-if` 条件：仅在主分支 push 时保存缓存，PR 只读不写（避免 cache 膨胀）
- **实现细节**：
  - check-rust 编译产物（debug）可部分被 release build 复用（依赖 .d 文件和 incremental 数据）
  - 为 check-rust 添加 `shared-key` 后，build-agent/build-hub 的 rust-cache 可命中 check 阶段的部分产物
  - `save-if: ${{ github.event_name == 'push' && github.ref == 'refs/heads/main' }}` 减少缓存污染
- **测试标准**：第二次 CI 运行时，rust-cache 步骤显示 `Restored cache` 且编译步骤时间明显缩短
- **提交信息**：`ci: tune rust-cache shared-key and save-if for better hit rate`

### 3 构建矩阵并行度优化

- **功能目标**：减少 build-hub 对 build-frontend 的串行等待，最大化构建并行度
- **文件结构**：修改 `.github/workflows/ci.yml`
- **接口设计**：
  - 当前 build-hub 依赖 `needs: [check-rust, build-frontend]`，而 build-frontend 依赖 `needs: [check-web]`
  - 优化：build-hub 只需要 check-rust 和 build-frontend，但 build-hub 中下载 frontend artifact 的步骤可以条件化
  - 方案：build-hub 的 `needs` 仅保留 `check-rust`，将 frontend artifact 下载放在 docker-hub 步骤中（因为 Docker 构建才真正需要 frontend 产物）
  - 实际上，build-hub 编译的是 Rust 二进制，不需要 frontend dist，只有 docker-hub 才需要
- **实现细节**：
  - 将 `build-hub` 的 `needs` 从 `[check-rust, build-frontend]` 改为 `[check-rust]`
  - 将 `docker-hub` 的 `needs` 从 `[build-hub, build-frontend, build-agent]` 保持不变（它确实需要全部产物）
  - 这样 build-hub 可以和 build-frontend 并行执行，而非等待 build-frontend 完成
- **测试标准**：CI pipeline 的关键路径上，build-hub 不再等待 build-frontend；总构建时间缩短约 3-5 分钟
- **提交信息**：`ci: decouple build-hub from build-frontend for better parallelism`

### 4 交叉编译优化

- **功能目标**：将 aarch64-unknown-linux-gnu 的交叉编译从 `cross` 工具切换到 `cargo-zigbuild`，缩短编译时间
- **文件结构**：修改 `.github/workflows/ci.yml`
- **接口设计**：
  - build-agent job 中 aarch64-unknown-linux-gnu 的 `cross: true` 条件改为安装 cargo-zigbuild
  - 安装 Zig（作为 cargo-zigbuild 的后端）：`sudo snap install zig --classic` 或从 GitHub release 下载
  - 安装 cargo-zigbuild：`cargo install cargo-zigbuild`
  - 构建命令从 `cross build` 改为 `cargo zigbuild`
  - 设置 linker：`CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=aarch64-linux-gnu-gcc` 可能不再需要（zigbuild 自带 linker）
- **实现细节**：
  - cargo-zigbuild 使用 Zig 作为交叉编译工具链，比 cross（基于 Docker）更快
  - Zig 安装更快（单二进制），无需拉取 Docker 镜像
  - 保持与现有 Cargo.toml target 配置兼容
  - 备选方案：如果 zigbuild 有兼容性问题，保持 cross 但优化 Docker image 缓存
- **测试标准**：aarch64-unknown-linux-gnu 构建成功，构建时间从约 10 分钟降至 5-7 分钟
- **提交信息**：`ci: switch aarch64 cross-compile to cargo-zigbuild`

### 5 测试与收尾

- **功能目标**：验证所有优化生效，记录构建时间对比
- **文件结构**：修改 `.github/workflows/ci.yml`（无额外文件）
- **实现细节**：
  - 检查 CI YAML 语法正确性（`actionlint` 或手动验证）
  - 检查所有 job 的依赖关系无循环
  - 确认 Docker cache-from/to 配置格式正确
  - 确认 rust-cache shared-key 不冲突
  - 确认 build-hub 的 needs 变更后 docker-hub 仍能正确获取所有 artifact
- **测试标准**：所有 GitHub Actions job 定义正确，无语法错误
- **提交信息**：`ci: verify and finalize build optimizations`
