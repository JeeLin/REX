# M16 步骤2：设计核对报告

## 审查维度

### 1. 产品定位

- [x] **单用户** — 无多用户、RBAC、企业协作概念
- [x] **自托管** — 更新机制完全在用户控制下，不依赖外部 SaaS
- [x] **深色优先** — 不涉及 UI 变更

### 2. 架构一致性

- [x] **进程模型** — 简化为直接重启（`std::process::exit(0)` + 外部管理器），不引入 supervisor/worker，符合 M16 范围
- [x] **单二进制** — Agent 仍是单二进制，更新替换的是整个二进制
- [x] **共享 crate** — 更新逻辑放在 `rex-common/src/update.rs`，Hub 和 Agent 共享

### 3. 功能边界

| 检查项 | 结论 |
|--------|------|
| M16 做什么清晰？ | ✅ 版本检查 + 更新触发 + 下载校验替换 + Docker 打包 + 前端展示 |
| M16 不做什么明确？ | ✅ 不做 supervisor/worker、不做 Hub 自动更新、不做自动回滚轮询 |
| 是否引入后续里程碑功能？ | ❌ 无 — TLS 是 M17、Agent 日志远程查看未涉及 |
| 是否跳阶段？ | ❌ 无 — 按 DEVELOPMENT.md 规划推进 |

### 4. 设计合理性

| 设计点 | 评估 |
|--------|------|
| 更新触发方式（Hub → Agent WebSocket） | ✅ 利用现有 WebSocket 连接，无需新增 REST 端点 |
| 下载优先级（Hub → GitHub fallback） | ✅ 符合用户要求："优先从 hub 下载，hub 没有才从 github" |
| SHA256 校验 + 原子替换 | ✅ 安全可靠 |
| 多架构支持（x86_64 + aarch64） | ✅ 覆盖主流 Linux 架构 |
| 更新状态跟踪（phase + progress） | ✅ 足够前端展示进度 |
| auto_update 开关 | ✅ 符合产品文档 3.10 节 |
| 备份机制（.bak 文件） | ✅ 简单有效 |

### 5. 无概念污染

- [x] 无 RBAC、多用户
- [x] 无企业协作
- [x] 无 SaaS 依赖
- [x] 文件传输不经过浏览器（更新二进制直接替换，不涉及传输）

**✅ 通过**

M16 里程碑文档设计合理，功能边界清晰，与产品定位一致，无概念污染。可以进入步骤3开发。
