# 0.70.1: 浏览器实时双向音频（Opus-over-WebSocket 媒体通道）

## Context

M82a（v0.70.0）完成 SIP 信令层：register/dial/answer/hangup/hold/unhold/dtmf + 事件流，Hub/Agent 共用 baresip FFI 当 UA₁/UA₂，前端 `features/sip/` 拨号盘 + 通话状态。但音频流（RTP）在 M82a 仅留 `SipUaTrait::on_rtp` 空桩接口。

本阶段打通**浏览器实时双向音频**：Hub（或 Agent UA₂）侧终止 RTP，将 PCM 编码为 Opus，经 WebSocket 媒体通道实时推流到浏览器；浏览器用 Web Audio 解码播放，麦克风经 `getUserMedia` 采集、反向编码回传，实现浏览器与对端**实时双向**通话（满足「时时对话」）。

**产品原则例外说明**：PRODUCT.md 第 430 行规定「数据在 Hub/Agent/远端之间传输，不经过浏览器」——音频媒体是此原则的**显式例外**（DEVELOPMENT.md M82b 已确认：用户明确要求浏览器实时听/说，媒体为实时流而非批量文件传输，与「文件传输不经过浏览器」的初衷不冲突）。本里程碑所有信令/控制/媒体帧仍经 Hub/Agent 服务端中转，浏览器只作为媒体端点，不接触远端 SIP 服务器。

版本类型：minor（SIP 功能的延续增强，向后兼容，无破坏性变更）

## 产品边界

### 本阶段做什么
- baresip 音频接管：在 baresip 事件线程内从 `call_audio()`/`auframe` 抽取接收 PCM、向发送侧喂 PCM（接管默认 audio 设备，避免依赖系统 alsa/coreaudio）；接 `on_rtp` 钩子回调。
- Hub 侧 RTP→Opus 编码管线（发送链路）：从 UA 抽取 PCM → Opus 编码 → 媒体帧经 `/ws/sip` 推浏览器。
- `/ws/sip` 媒体通道：新增 binary 媒体帧协议（与现有文本信令帧区分），支持 Hub→浏览器下行 Opus 帧 + 浏览器→Hub 上行麦克风 Opus 帧。
- Agent UA₂ 媒体转发：隧道 binary 帧中区分「媒体」与「信令」，媒体帧经现有 `agent_ws.rs` 隧道回 Hub（复用 channel_id 多路复用，不新造隧道）。
- 前端 Web Audio 播放 + 麦克风采集（`getUserMedia`）+ Opus 解码（WebCodecs / opus 解码库），通话中可听可说。
- 延迟/回声基础优化（jitter buffer、回声抑制开关）+ 端到端联调（可听可说）。

### 本阶段不做什么
- 不实现 CDR/录音/信令抓包/展示图（属 M82c / 0.70.2）。
- 不改动信令层行为（M82a 已稳定的 register/dial/.../事件流保持不变）。
- 不改变 Hub/Agent 版本一致模型。
- 不引入多用户/ RBAC / 企业协作。

## 子任务详细设计

### 1 `crates/rex-sip` 音频链路

- **功能目标**：在 baresip 事件线程内接管音频——接收侧从 `call_audio(call)` 抽 `auframe` PCM 经 `on_rtp` 回调上抛；发送侧新增 `send_audio` 把浏览器麦克风 PCM 喂回 baresip 发送链路。opus 作为编解码依赖。
- **文件结构**：
  - `crates/rex-sip/Cargo.toml`（加 `opus = { workspace = true }` 或 `audiopus`；workspace.dependencies 加 `opus`）
  - `crates/rex-sip/src/lib.rs`（`SipUaTrait` 改 `on_rtp` 为接收钩子 + 新增 `async fn send_audio(&self, pcm: Vec<i16>) -> Result<()>`；`on_rtp` 默认实现移除 no-op 注释，改为可注册）
  - `crates/rex-sip/src/baresip_ua.rs`（`bevent`/`call` 事件线程内接 `call_audio` + `au` 模块抽 PCM 帧；注册 `on_rtp` 回调；新增 `send_audio` 经 mqueue 主线程序列化喂 PCM 到 baresip 发送侧——复用 M82a 的 mqueue 单线程模型，避免跨线程竞争）
  - `crates/rex-sip/src/mock.rs`（Mock 记录 `send_audio` 调用，便于 handler 单测）
- **接口设计**：
  ```rust
  // 接收：baresip 事件线程内每收到一帧 PCM 调用（采样 i16，单/双声道按 config）
  fn on_rtp(&self, cb: impl FnMut(&[u8] /*pcm*/) + Send + 'static);  // 沿用 M82a 钩子签名
  // 发送：浏览器麦克风 PCM 回传
  async fn send_audio(&self, pcm: Vec<i16>) -> anyhow::Result<()>;
  ```
  baresip 音频采样约定：8000Hz mono PCM i16（G.711/PCMU 链路），或按 `account_set_audio_codecs` 协商的 Opus；M82b 先以 8000Hz mono i16 内部 PCM 统一，opus 仅作线上编码。
- **后端流程**：baresip 事件线程在 `BEVENT_CALL_ESTABLISHED` 后启动音频抽取循环（经 `call_audio`/`au` 模块），每帧 PCM 调 `on_rtp` 回调；`send_audio` 经 mqueue 主线程序列化，喂 PCM 到 baresip 音频发送侧（`au` 播放源）。M82a 的「单例运行时 + mqueue 主线程序列化 + 无跨线程竞争」模型继续适用。
- **测试标准**：Mock `send_audio` 记录调用（`mock.rs` 单测）；baresip 真链路需真 SIP server + 音频设备模拟（联调验证，CI 不覆盖）。`cargo build`/`cargo test` 全绿。
- **提交信息**：`feat: rex-sip audio link: on_rtp hook + send_audio (0.70.1 #1)`

### 2 Hub `/ws/sip` 媒体通道

- **功能目标**：`/ws/sip` 复用同一 WebSocket，新增 binary 媒体帧（与文本信令帧区分），下行 Opus 帧推浏览器、上行麦克风 Opus 帧收浏览器。
- **文件结构**：
  - `crates/rex-hub/src/sip_ws.rs`（新增 `handle_sip_session`/`handle_agent_sip` 媒体分支：注册 `on_rtp` 回调 → Opus 编码 → `Message::Binary` 推浏览器；收 `Message::Binary` 上行帧 → Opus 解码 PCM → `ua.send_audio`）
  - 新增媒体帧类型（line 格式区分）：binary 帧首字节或 JSON 包装 `{type:"media", dir:"down"|"up", payload:<base64/raw opus>}`
- **接口设计**（媒体帧，复用 `/ws/sip`，与信令 `ClientMsg`/`ServerMsg` 文本帧并存）：
  - Hub→浏览器下行：`Message::Binary(opus_frame)`（或 `{type:"sip.media", dir:"down", payload: <base64 opus>}` 文本包，优先 binary 降低开销）
  - 浏览器→Hub 上行：`Message::Binary(opus_mic_frame)`
  - 鉴权复用现有 JWT query token。
- **后端流程**：`handle_sip_session` 注册 `on_rtp` → Opus 编码 → `ws_sink.send(Binary)`；前端 Binary 帧 → Opus 解码 → `ua.send_audio(pcm)`。`handle_agent_sip`（Agent 链式）把媒体帧经隧道 binary 帧（channel_id 前缀 + `media` 标记）转发给 Agent UA₂，Agent UA₂ 的 `on_rtp` 回传同样经隧道回 Hub。
- **测试标准**：`sip_ws.rs` 用 Mock `SipUa` 测 `on_rtp` 回调触发下行帧、`send_audio` 被上行帧调用（handler 单测）；opus 编解码 round-trip 单测。
- **提交信息**：`feat: hub /ws/sip media channel: opus down/up over binary frames (0.70.1 #2)`

### 3 Agent UA₂ 媒体转发

- **功能目标**：Agent 内 UA₂ 接管音频后，媒体帧经现有 `agent_ws.rs` 隧道（channel_id 多路复用 + binary 帧）回 Hub，与信令帧共用通道但用 `media` 标记区分。
- **文件结构**：
  - `crates/rex-agent/src/agent_ws.rs`（`run_sip_ua2` 注册 `on_rtp` → 经 `data_tx` 隧道发媒体 binary 帧；收隧道 media 帧 → `ua.send_audio`；复用 M82a 的数值 `AGENT_CHANNEL_SEQ`）
- **接口设计**：隧道 binary 帧 `[4B channelId][1B kind][payload]`，`kind=0` 信令（SipEvent JSON）/ `kind=1` 媒体（Opus/PCM）。沿用 M82a 隧道，仅扩展 kind 字节。
- **后端流程**：Agent `run_sip_ua2` 起 UA₂ 并注册 `on_rtp`，媒体帧经 `data_tx` 发隧道；Hub `handle_agent_sip` 区分 kind=1 帧 → Opus 编码推浏览器；上行浏览器帧 → 隧道 kind=1 → Agent `ua.send_audio`。
- **测试标准**：Agent `run_sip_ua2` 媒体帧经隧道进出单测（mock 隧道 channel，断言 media kind 正确标记 + 字节经 data_tx 进出）。
- **提交信息**：`feat: agent UA2 media relay over channel-multiplexed tunnel (0.70.1 #3)`

### 4 前端 `api/sip.ts` 媒体通道 + `SipPage` 音频组件

- **功能目标**：浏览器接 `/ws/sip` 媒体帧，Web Audio 解码播放；`getUserMedia` 采麦克风，Opus 编码回传；通话中可听可说，挂断清理。
- **文件结构**：
  - `packages/rex-console-web/src/api/sip.ts`（新增媒体通道：区分 Binary 媒体帧 / 文本信令帧；Web Audio `AudioContext` 播放 + `MediaStreamSource`；`getUserMedia` 采集 + opus 编码；`sendAudio(opusFrame)`）
  - `packages/rex-console-web/src/features/sip/SipPage.vue`（通话 Active 时显示音频控制：麦克风开关、扬声器/静音；挂断时 `closeAudio` 清理 `AudioContext`/`MediaStream`）
  - `packages/rex-console-web/src/features/sip/CallState.vue`（激活态加音频控制按钮：麦克风开关）
- **接口设计**：`SipClient` 新增 `onMedia` 回调 + `startMic()`/`stopMic()`/`sendAudio(frame)`；opus 解码用 WebCodecs `AudioDecoder`(opus) 或 `opus.js`；编码用 `AudioEncoder`(opus) 或 `opus.js`。
- **交互设计**：通话 Active → 自动/手动开麦 → 浏览器实时播放对端音频 + 麦克风实时回传；静音按钮切 `MediaStreamTrack.enabled`；挂断 → 关闭 `AudioContext`、停 `getUserMedia`、清回声。复用 `components/ui/*` 与设计 token。
- **前端流程**：`handleEvent` 收到 `call_state:Active` → 建 `AudioContext` + 等媒体帧解码播放；`startMic()` → `getUserMedia` → 采集 PCM → opus 编码 → `sendAudio` 上行。
- **测试标准**：组件测试验证通话 Active 触发音频初始化、挂断触发清理；`api/sip.ts` 媒体帧编解码单测（opus round-trip mock）。
- **提交信息**：`feat: frontend sip real-time audio: web audio playback + mic capture (0.70.1 #4)`

## 设计核对点

- 单用户、自托管定位不被破坏（音频端点仍是单一用户本地浏览器，无多租户）。
- 不引入 RBAC/多用户/企业协作。
- **PRODUCT.md 430 行「媒体不经过浏览器」的显式例外**：本里程碑浏览器作为实时音频端点（用户明确要求可听可说），所有帧仍经 Hub/Agent 服务端中转，浏览器不接触远端 SIP 服务器，与「文件传输不经过浏览器」初衷不冲突——此为 DEVELOPMENT.md M82b 已确认的例外，步骤2 核对时以此为准，不视为违反产品边界。
- 信令层（M82a 稳定的 register/dial/.../事件流）行为不变，本里程碑仅增媒体通道。
- 音频链路复用 M82a 的 baresip 单例运行时 + mqueue 主线程序列化模型，send_audio 同样经 mqueue 串行化，避免跨线程竞争（延续 M82a 线程安全结论）。
- Agent 媒体转发复用现有 `agent_ws.rs` 隧道（channel_id 多路复用 + binary 帧，仅扩展 kind 字节区分媒体/信令），不新造隧道。
- 前端改动统一用设计 token，不硬编码 hex。
- opus 编解码：线上用 opus（带宽友好），内部 baresip PCM 统一 8000Hz mono i16（与 baresip 默认音频管线对齐）。
