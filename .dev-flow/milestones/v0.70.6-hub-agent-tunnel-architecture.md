# v0.70.6：统一 Hub↔Agent 隧道架构（Agent 终结协议、Hub 仅作传输隧道）

## Context
前序阶段（M82a–f / 0.70.0–0.70.5）完成了软电话 SIP 资源，并验证了「单条 WebSocket + `channel_id` 多路复用」的 Hub↔Agent 隧道范式（SIP 的 UA₂ 已正确经该隧道链式转发）。但此前的 SSH / SQL / Redis / 文件(S3/SFTP) 资源在 agent 模式下**并未真正走通**：

- **SSH via agent**：agent 确实向目标发起 TCP（`agent_ws.rs` 的 `TcpStream::connect`），但 Hub 只对裸字节做桥接（`handle_agent_terminal`），**未运行 russh**——用户因此看到服务端横幅 `SSH-2.0-OpenSSH_...` 后无 shell。
- **SQL / Redis / 文件(S3/SFTP) via agent**：Hub 侧连接器（`sql_api` / `redis_api` / `file_api`）**直接 `rex_*.connect` 从 Hub 连目标**，根本未挂 agent 隧道；若目标仅在私网（agent 可达、Hub 不可达），则 agent 模式对这些协议形同虚设。

本阶段把协议终结从 Hub **下沉到 Agent**：Agent 成为私网内的「协议执行引擎」，Hub 退化为通用传输隧道 + 控制面 + UI。这与产品定位「Agent 是内网反向代理、目标机不开放入站端口」一致，也接上 CLAUDE.md 的 supervisor+worker 模型。传输层仍复用现有的**单条 WebSocket + `channel_id` 多路复用**（已具备，不再新建通道）。

版本类型：minor（向后兼容，前端连接树/工作空间交互无变化，仅 agent 模式资源真正可用）。

## 产品边界
**本阶段做什么**
- Agent 内终结 SSH（russh，含 PTY/认证/resize）、SQL（sqlx：mysql/postgres/sqlite）、Redis、文件（S3 / SFTP）协议。
- 定义 Hub↔Agent 的「协议会话」结构化消息契约（终端流 / 查询请求-响应 / 文件分块传输）。
- Hub 隧道侧重构：agent 资源一律经隧道送达 Agent 执行，Hub 不再为 agent 资源直连目标。
- 收敛凭据传输：明确 connect 消息中 `password`/`privateKey` 的信任边界（明文经加密 WS 下发 Agent，由 Agent 使用；Hub 侧不再持有已终结的会话明文）。
- 复用并固化现有单 WS 多路复用，补集成测试。

**本阶段不做什么**
- 不改变前端连接树 / 工作空间的任何交互（协议下沉对前端透明）。
- 不引入多用户 / RBAC / 企业协作概念（AGENTS.md 硬性约束）。
- 不改动 SIP 资源（M82a–f 已实现并经隧道转发，沿用其 `channel_id` 范式）。
- 不改变单二进制 + supervisor + worker 进程模型。
- 不新增资源类型（仍 8 种：ssh/sql/redis/s3/sftp/sip/...）。

## 子任务详细设计

### 1 隧道契约固化
- **功能目标**：确认并锁定「单 WS + 二进制帧 `[4B u32 channelId][data]` + `LocalChannel` 路由」现状（已存在于 `crates/rex-agent/src/agent_ws.rs` 与 `crates/rex-hub/src/agent_ws.rs` 的 `tunnel_data`），为 2–7 提供稳定底座。
- **文件结构**：
  - 修改：`crates/rex-agent/src/agent_ws.rs`（channel_id 分配、帧路由）
  - 新增：`crates/rex-agent/tests/tunnel_mux.rs`（集成测试）
- **交互设计**：无前端变更。
- **后端流程**：起 Hub + Agent，经隧道开 2 个并发 SSH/SIP 会话，断言双向数据按 channelId 正确隔离、不串帧；断言 WS 断开后所有会话被回收。
- **测试标准**：并发多会话隔离通过；帧边界（`[4B channelId]` 大小端）单测通过；`cargo test -p rex-agent` 绿。
- **提交信息**：`test(agent): pin single-WS channel_id multiplexing with integration test`

### 2 定义 Hub↔Agent「协议会话」消息 schema
- **功能目标**：在现有 `Text`(控制) / `Binary`(原始流) 之上，新增「协议会话」结构化消息，使 Agent 向上汇报**已终结协议**的结果而非裸字节。
- **文件结构**：
  - 新增：`crates/rex-common/src/agent_proto.rs`（会话消息枚举：`SessionOpen` / `TerminalData` / `QueryRequest` / `QueryResponse` / `FileChunk` / `SessionError` / `SessionClose`，统一 `request_id`/`channel_id` 路由键）
  - 修改：`crates/rex-hub/src/agent_ws.rs`、`crates/rex-agent/src/agent_ws.rs`（编解码）
- **接口设计**：消息以 `Text` JSON 承载控制/结构化数据；大体积文件分块走 `Binary` 帧（前缀复用 channelId）。`req_id` 关联前端请求，`channel_id` 关联 agent 隧道槽。
- **交互设计**：无前端变更（Hub 内部契约）。
- **后端流程**：Hub 收到前端 SSH/SQL/Redis/文件请求 → 封装为 `SessionOpen{protocol,config}` 经隧道下发 Agent → Agent 执行协议并以 `TerminalData`/`QueryResponse`/`FileChunk` 结构化回传 → Hub 直接转给前端 WebSocket。
- **测试标准**：schema 往返（serde）单测；Hub/Agent 两侧编解码一致性单测。
- **提交信息**：`feat(common): define hub<-agent protocol-session message schema`

### 3 Agent 协议执行层 + 修 SSH bug
- **功能目标**：Agent 内嵌 russh 客户端，对 SSH 资源在 Agent 侧完成握手/认证/PTY，取代 `handle_agent_terminal` 的裸字节桥接（修掉 banner 卡死）。
- **文件结构**：
  - 修改：`crates/rex-agent/Cargo.toml`（引入 `rex-ssh` 或 russh 依赖）
  - 修改：`crates/rex-agent/src/agent_ws.rs`（`handle_connect` 的 ssh 分支：建协议会话而非裸 TCP）
  - 修改：`crates/rex-hub/src/terminal_ws.rs`（`handle_agent_terminal`：改为消费 `TerminalData` 结构化流，移除裸桥）
- **后端流程**：
  1. Hub 发 `SessionOpen{protocol:"ssh",config:{host,port,username,password,privateKey}}`；
  2. Agent 用 russh 连目标（Agent 在私网，可达），做认证 + 开 PTY；
  3. Agent 将 shell 的 stdin/stdout/stderr 以 `TerminalData` 经隧道回传；前端键入经 `Data` 下发 Agent → russh `send_data`；
  4. resize 走 `Resize{cols,rows}`。
- **测试标准**：本地起 Hub+Agent+一个测试 SSH 容器，经 agent 模式能进入交互 shell（不再出现裸 banner）；`cargo test` 绿。
- **提交信息**：`fix(agent): run russh in agent for ssh, drop raw-byte bridge`

### 4 Agent 终结 SQL
- **功能目标**：SQL 资源经 agent 模式时，由 Agent 内 sqlx 执行，结果经 `QueryResponse` 回传。
- **文件结构**：
  - 修改：`crates/rex-agent/Cargo.toml`（引入 `rex-mysql`/`rex-postgresql`/`rex-sqlite` 或 sqlx）
  - 修改：`crates/rex-agent/src/agent_ws.rs`（sql 分支协议执行 + 结果序列化）
  - 修改：`crates/rex-hub/src/sql_api.rs`（`use_agent` 分支改为经隧道下发，移除直连）
- **后端流程**：Hub 识别 `resource.connection_mode=="agent"` → 不走 `rex_mysql::connect`，改为发 `SessionOpen{protocol:"sql",config}`；Agent 执行查询并以 `QueryResponse{columns,rows,error}` 回传。
- **测试标准**：agent 模式下对私网测试库跑 SELECT 成功；直连模式行为不变。
- **提交信息**：`feat(agent): execute sql in agent, relay results over tunnel`

### 5 Agent 终结 Redis
- **功能目标**：Redis 资源经 agent 模式时由 Agent 内 redis 客户端执行。
- **文件结构**：
  - 修改：`crates/rex-agent/Cargo.toml`（引入 `rex-redis` 或 redis crate）
  - 修改：`crates/rex-agent/src/agent_ws.rs`（redis 分支）
  - 修改：`crates/rex-hub/src/redis_api.rs`（`use_agent` 分支走隧道）
- **后端流程**：同 SQL，命令/响应经 `QueryResponse` 结构化传输。
- **测试标准**：agent 模式连私网 redis 执行 GET/SET 成功。
- **提交信息**：`feat(agent): execute redis in agent, relay over tunnel`

### 6 Agent 终结 文件 S3 / SFTP
- **功能目标**：文件传输（S3 / SFTP）经 agent 模式时由 Agent 执行；满足「文件传输数据不经过浏览器」（AGENTS.md 约束）——Agent 直接对目标做分块读写，仅分块元数据/进度经隧道。
- **文件结构**：
  - 修改：`crates/rex-agent/Cargo.toml`（引入 `rex-ssh` sftp / `rex-s3` 或 s3 sdk）
  - 修改：`crates/rex-agent/src/agent_ws.rs`（file 分支：SFTP/S3 协议执行 + `FileChunk` 流）
  - 修改：`crates/rex-hub/src/file_api.rs`（`use_agent` 分支走隧道）
- **后端流程**：Hub 下发 `SessionOpen{protocol:"file",config:{kind:"sftp"|"s3",...}}`；Agent 直接读写目标文件，以 `FileChunk{offset,data}` 经隧道回传（Hub 中转给前端展示进度/落盘）。
- **测试标准**：agent 模式 SFTP 列目录/上传、S3 列桶/下载成功；数据不落浏览器。
- **提交信息**：`feat(agent): execute sftp/s3 in agent, stream chunks over tunnel`

### 7 Hub 隧道侧重构 + 凭据信任边界
- **功能目标**：统一 agent 资源入口——Hub 不再为任何 agent 资源直连目标；明确 connect 消息中 `password`/`privateKey` 的信任边界。
- **文件结构**：
  - 修改：`crates/rex-hub/src/{sql_api,redis_api,file_api,terminal_ws}.rs`（移除 `use_agent` 直连分支，统一经 `agent_ws` 隧道）
  - 修改：`crates/rex-common/src/agent_proto.rs`（connect 消息增加 `trust_boundary` 标注：凭据明文仅经加密 WS 下发 Agent，由 Agent 使用）
- **后端流程**：所有 `connection_mode=="agent"` 的资源 → 经 `agent_tunnel` 下发 `SessionOpen`；Hub 不持有终结后的会话明文。
- **测试标准**：grep 确认 Hub 端无 `rex_*.connect` 在 agent 路径被调用；全协议 agent 模式集成测试绿。
- **提交信息**：`refactor(hub): route all agent resources through tunnel, fix credential trust`
